# Decisions and deviations

| # | Topic | Decision | Why |
|---|---|---|---|
| 1 | Language | JavaScript (ES modules) everywhere instead of TypeScript | Requested by the client |
| 2 | Repo layout | `backend/` and `frontend/` folders instead of npm workspaces with `shared/` | Requested; enums and labels are small enough to keep a copy on each side |
| 3 | Jobs | `node-cron` in the API process (or `npm run worker` as a separate process) instead of BullMQ + Redis | No Redis on the target machine. Jobs are idempotent and logged in `jobruns`, so moving to BullMQ later only changes the scheduler |
| 4 | Transactions | Stock movements use a MongoDB transaction when the server is a replica set and fall back to conditional atomic updates (`qty >= n`) on a standalone server | The local MongoDB is standalone; negative stock is still impossible |
| 5 | Validation | Zod on workflow endpoints (auth, tickets, check-in, stock); Mongoose schema validation plus a protected-field filter on generic master CRUD | Covers the same rules with much less code |
| 6 | Files | `lib/storage.js` has two adapters: local disk (`backend/uploads`, random 128-bit names) or S3 when `S3_BUCKET` is set. The API stores plain `/uploads/<name>` paths and signs them on the way out (HMAC with an expiry rounded to the hour, so links stay cache-friendly). It strips signatures from incoming bodies. With S3, a valid link redirects to a 5-minute presigned URL | Stored records never hold expiring URLs. Photos are private by default. The S3 bucket can stay fully private |
| 7 | PDF | Reports and POs are generated on the server with PDFKit (no headless Chrome). Reports are emailed as attachments; the print view stays for quick browser printing | A small dependency that works on any server. Built-in fonts can't draw ₹, so PDFs write "Rs." |
| 8 | Roster UI | Week grid with a shift picker in every cell plus "copy previous week" instead of drag-and-drop | Easier for first-time users, works on touch screens |
| 9 | QR | Stickers encode the deep link (`/assets/:id`), so any phone camera opens the asset. The app also has its own scanner (html5-qrcode) with a type-the-code fallback | Works with or without camera permission |
| 10 | i18n | Strings are English and written inline; i18next extraction is in Phase 5 | Keeps v1 small |
| 11 | Org model | Properties belong to the client organisation; org-level masters (items, vendors, categories, SLA policies, roles, KPI definitions) are scoped to the active property's organisation | Fits the multi-tenant requirement with one simple scope rule |
| 12 | Permissions | Spec matrix mapped to `module:action` strings with `*` and `*:read` wildcards; PM gets write access to inventory and procurement as well | The most practical reading of the matrix for site operations |
| 13 | Ticket "Open" | Open = every status except Tenant Confirmed, Closed and Cancelled (Resolved still counts until the tenant confirms) | Matches demo step 6: the tile drops when the tenant confirms |
| 14 | Priority suggestion | Suggested priority = the higher of the category default and asset criticality (critical→P1, high→P2, normal→P4) | Gives P2 for AHU-A-05 (HVAC, high criticality) as the deck expects |
| 15 | Offline scope | Only field actions are queued offline: check-in/out, ticket acknowledge/start/hold/resume, parts requests and job completion (photos are kept as blobs and uploaded at sync). Other edits need a connection. Reads use the service worker's network-first cache, and the screens a field user needs are pre-cached by permission | Covers what happens in basements and plant rooms without the conflict handling a full offline database would need |
| 16 | Offline time | Each queued action carries the tap time. The server accepts it up to 12 h back for attendance and 24 h back for job completion, never in the future. Anything synced more than 2 minutes late is flagged as offline for the supervisor | Attendance shows when people actually checked in, and flagging keeps it auditable |
| 17 | Sign-out when offline | A failed token refresh signs the user out only when the server rejected it, not when the network is down | Otherwise opening the app with no signal would log the technician out and discard the queue |
| 18 | Push | Standard Web Push (VAPID) via the service worker; no Firebase. Keys come from `.env`, or are generated once and stored in `systemsettings`. Expired subscriptions (404/410) are removed | No third-party account. Works on Android and on iPhone once the app is added to the Home Screen |
| 19 | SMS / WhatsApp | One `deliver()` with pluggable providers: console, Twilio, or a generic webhook. Indian SMS/WhatsApp gateways (MSG91, Gupshup, Meta Cloud API) differ per account, so they connect through the webhook. Each notification records per-channel delivery results | No vendor lock-in; failures are visible |
| 20 | Approval rules | Chains are `ApprovalRule` records per organisation (role + minimum amount per level), edited on screen. Built-in defaults apply when no rule exists, and an amount-based level is skipped when the amount is below it | Clients change limits without a code change |
| 21 | Email-to-ticket | A provider webhook (`/inbound/email?token=`) rather than polling an IMAP mailbox. Only registered senders create tickets; the category is picked by keywords | No mailbox credentials on the server; blocks spam tickets |
| 22 | Public API | Separate `/public` routes authenticated by hashed API keys (shown once) with per-key scopes and a rate limit. Each key belongs to one property | BMS/ERP systems get a small stable surface instead of the internal API |
| 23 | Daily log sheets | Daily critical-asset checks are work orders of type `daily_check`, generated from schedules with `kind: daily_check`. They close on completion without supervisor verification. Numeric readings are written to `MeterReading`, and a value outside its range raises a ticket | Reuses the PPM engine, mobile checklist and offline queue |
| 24 | Visual design | One token set in `frontend/src/theme.js`: indigo brand (`BRAND`) with a violet gradient accent, cool grey neutrals (`GREY`), soft tinted status colours (each with a `soft` background and an `ink` text shade at 4.5:1 or better), and shared `SHADOW` and `CHART` tokens. The sidebar is light. Headings use Plus Jakarta Sans and body text uses Inter, both bundled with the app so they work offline. Chart series are indigo and orange, checked for colour-blind separation | Re-skinning means editing one file. Status chips stay readable without depending on colour alone (dot or icon plus text) |
| 25 | Responsive layout | Three widths, one codebase. Under 600 px, the shared `DataTable` renders a tappable row list (title, status badges, four labelled fields, Previous/Next) instead of the grid. Hand-written tables use `StackTable`, which turns each row into a labelled card, taking the labels from the header row. Today's rows adapt to their card's width with CSS container queries, so half-width cards on tablets stack too. The sidebar is permanent from 900 px; below that it slides in | Every list screen became phone-friendly without per-page work, and tablets keep the full grid. Checked by an automated audit of every role's screens at 390, 820 and 1180 px: no screen scrolls sideways |
| 26 | Self-service attendance | `/attendance/my`, check-in and check-out are allowed for any login linked to an employee record, whatever the role. Marking someone else's attendance still needs `attendance:approve` | Helpdesk, stores, procurement and HSE staff are rostered too. Before this change they saw My check-in but got "forbidden", and would have been marked absent |
| 27 | User management | The user form also sets properties, vendor and tenant links. A Property Manager can only grant properties they hold, and only a Super Admin can grant the Super Admin role | Vendor and tenant logins can be created on screen, and access cannot be widened beyond the creator's own |
| 28 | Phone menu and page switching | <ul><li>The phone/tablet menu is built once and kept mounted.</li><li>Its open state lives in a small store outside the layout, so opening it never re-renders the page.</li><li>The page area has its own loading boundary, and navigations run as React transitions, so the current page stays until the next is ready.</li><li>Menu links replace the menu's history entry, so the phone's Back button closes the menu instead of leaving the page.</li><li>Swipe left closes the menu, and tap targets are 46 px.</li><li>Only Overview, Helpdesk and the current page's group start expanded, and the current page is scrolled into view.</li><li>After sign-in, page code loads in idle time (skipped with Data Saver on).</li><li>A compositor-only top bar shows that a page is opening.</li><li>Blur effects are desktop-only, and `useMediaQuery` reads the screen size on the first render.</li></ul> | Testing on a 4×-slowed CPU found the menu took about 5 s to open. Opening the first page from the menu suspended the whole app: a full-screen spinner showed, and the menu's overlay stayed over the page and swallowed taps. Now the menu opens in about 0.3–0.4 s on the same CPU and never blocks the page |
